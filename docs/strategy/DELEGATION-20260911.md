# 推進計画：ファウンダーの手離れをどう作るか

2026-09-11。ファウンダーの問い「アイデアも構築実装も運用改善も、全部任せていいか」への回答。

結論から言う。**運用と実装の大半は任せてよい。ただし4つは私に渡してはいけない。**
渡せない理由は私の能力ではなく、**間違えたときに誰が責任を負うか**である。

そして、いま手離れを妨げているのは承認の回数ではない。
**既存の自動化が事後検知であること**。ここを先に直さないと、任せるほど危なくなる。

---

## 1. 渡してはいけない4つ

### (1) 権利の最終判断

`tools/check-videos.js` は自分でこう書いている。
**「APIは『そのチャンネルが権利者本人か』を答えない。そこは人が判断する。」**

私が確かめられるのは「公開されているか」「埋め込めるか」まで。
その動画を上げた人が権利を持っているかは、API では分からない。
ここを間違えると権利侵害になり、取り消しがきかない。

同じことが画像・音源にも当てはまる。`CLAUDE.md` の
「Rights 不明の画像・映像・音源を使わない」は、私が守れるが、
**「不明かどうか」の最終判定は人が要る。**

### (2) 何を作るかの定義

Product meaning / Brand / Art Direction / Visual Canonical。
これを私に渡すと、製品が少しずつ別のものになる。
一回ごとの変化は小さいので、誰も気づかないまま遠くへ行く。

現に `CLAUDE.md` は、V1/V2 の「私的な書店」を現在の定義として復活させるな、と
名指しで禁じている。**過去に一度ずれた履歴がある。**

### (3) 本番反映の GO と、KILL の判断

`main` への merge と Production deploy。これは責任の所在の問題で、
技術的な可否ではない。私はテストが緑であることまでしか保証できない。
「出してよいか」は事業の判断である。

### (4) 世に出る文言の最終責任

`hook` と「なぜこの街か」。今日13件の下書きを書いたが、
それは**その都度あなたに確かめたうえで**書いた。
下書きは任せてよい。最終責任は編集部に残る。

---

## 2. いま手離れを妨げているもの

承認の回数ではない。**自動化が事後検知であること**である。

### 9/21 問題は、仕組みがあったのに見えなかった

催しの再確認は既に週2回動いている（`culture-events-review.yml`、
月曜と金曜）。それでも「9/21 に公開中24件が一度に消える」ことは
誰も気づかないまま、10日前になって見つかった。

理由は二つとも、道具の作りにある。

```js
// tools/review-culture-events.js
const expired = events.filter(e => e.reviewThrough < today)
```

**`< today`。** 期限が切れてから鳴る。切れる前には鳴らない。

そして coverage は今週と来週の2週しか見ない。9/11 の時点で
9/21 の週は「再来週」なので、視野の外だった。

`qa/event_supply_check.js` も、FAIL 判定は今週・来週だけである。

### 同じ形は、いまも残っている

今日の補充を終えたあとの状態を、期限の日ごとに数えるとこうなる。

```
2026-09-12   1日後   1件
2026-09-20   9日後  18件  ← まだ固まっている
2026-09-22  11日後   1件
2026-09-23  12日後   3件
（以下、1〜3件ずつ 11/03 まで散る）
```

**9日後に18件が同時に切れる。** この18件は会期が9/20より前に終わるので
実害は出ないが、「一日に固まっている」という形そのものは残っている。
先回りの検知があれば、これは今日すでに鳴っているべきものである。

いまの仕組みは、**公開面が寂しくなってから**知らせる。
ファウンダーが見たときには、もう読者も見ている。
この状態で手を離すと、事故に気づくのが遅れるだけになる。

**先に直すのはここ。** 任せる範囲を広げるのは、そのあとでよい。

---

## 3. 段階

### Phase 1：検知を先回りにする（私だけで完結する）

- `review-culture-events.js` の期限判定を「切れた」から「N日以内に切れる」へ。
  今日の実測で言えば、9/11 の時点で「9/20 に18件が同時に切れる」と鳴るべきだった
- 視野を2週から6週へ。`event_supply_check.js` は既に6週の見通しを出しているので、
  同じ数え方に揃える
- **同じ日に固まっている期限を異常として鳴らす。** 全件が同じ日という状態そのものが、
  在庫の作り方を間違えている印だった
- 時点を固定しているテストを、データから日付を導く形へ。
  いま `qa/weekly_outings_check.js` などは `2026-09-11` を直接書いている。
  データを更新するたびに人が書き換える必要があり、**手離れの邪魔になる**

これは判断を要さない。承認をもらえば私が進める。

### Phase 2：検知したら私が直すところまで

いまは Actions が知らせるだけで、直すのは人（か、人が起こしたセッション）である。
ここを繋ぐ。

- 週次で私が動き、在庫の薄い週を公式ページから補充し、ブランチへ push する
- テストが緑でなければ push しない。緑でも `main` には触らない
- あなたは**ブランチを見て GO を出すだけ**になる

手段は二つある。GitHub Actions から起こすか、Routine（定時実行）を組むか。
どちらも既存の枠組みで足りる。

### Phase 3：承認の粒度を下げる

ここが本丸である。**1件ずつ承認をもらうのをやめ、基準を一度もらう。**

今日の「下書きまで作ってよい」は、まさにそれだった。
一度決めたので、13件について13回聞かずに済んだ。

同じことを他にも広げる。

- **催しの採否基準** — `SELECTION-20260910.md` を、私が機械的に適用できる形に書き直す。
  満たせば採用、迷えば止める
- **文言の型** — 今日の19件が事例になる。型を決めれば、私は型の中で書ける
- **事前承認の範囲を `CLAUDE.md` に書く** — 例：「催しの補充は、公式ページで8項目を
  確認し、テストが緑なら、ブランチへの push まで承認不要」

そのうえで、**人にしか決められないものを1箇所に集める。**
いまは引き継ぎ書の §7 と §8 に散っている。これを一つのキューにして、
あなたは週に一度そこだけ見る。

---

## 4. 任せてよい範囲（Phase 3 まで進んだとき）

| | 誰が |
|---|---|
| 催しの発見・事実確認・補充 | 私 |
| 期限の再確認と延長 | 私（公式ページが開けるかぎり） |
| 文言の下書き | 私（型の中で） |
| テストの契約更新、回帰の修正 | 私 |
| 在庫・リンク・動画の監視 | 私（自動） |
| 実装、リファクタ、QA | 私 |
| **権利の最終判定** | **あなた** |
| **文言の最終責任** | **あなた**（型を決めたあとは抜き取りでよい） |
| **Product meaning / Brand / Art Direction** | **あなた** |
| **main merge / Production deploy / KILL** | **あなた** |

週に一度、キューを見て GO を出す。それが残る仕事になる。

---

## 5. 正直に言っておくこと

**私は自分の間違いに気づけないことがある。**

今日それが起きた。「女優魂2026 は上映日程が PDF にしかないから載せられない」と
判断して見送ったが、実際は特集ページの HTML に、作品ごとの上映日が
そのまま載っていた。見落としである。あなたが「開発を進めて」と言わなければ、
そのまま引き継ぎ書に誤った理由が残っていた。

だから手離れの設計には、**私が間違えても止まる仕組み**が要る。
テストがその役目を負っているが、テストは私が書き換えられる。
`CLAUDE.md` の「テストを削除・skip して緑にしない」が効いているのは、
それが明文化されているからである。

任せる範囲を広げるときは、同時に**私が越えてはいけない線を明文化する**。
線が書いてあれば守れる。書いていなければ、私は自分の判断で越える。
