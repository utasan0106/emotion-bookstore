# 自走の範囲と、越えてはいけない線

2026-09-11。ファウンダーが Phase 2 / Phase 3 を承認したうえで、
「越えてはいけない線は自分で判断して明文化せよ」と指示した。これはその回答である。

`CLAUDE.md` が正本であり、この文書はそれを狭める方向にしか働かない。
`CLAUDE.md` と矛盾したときは `CLAUDE.md` が勝つ。

**私が自分で自分を縛る文書なので、迷ったら厳しい側に倒してある。**
緩める改定は、私の判断では行わない。ファウンダーの承認が要る。

---

## 1. 承認なしに進めてよいこと

いずれも「テストが緑」「スコープ内」「記録を残す」が前提。
成果はブランチへ push するところまでで、**`main` には触れない。**

| やってよいこと | 条件 |
|---|---|
| 催しの補充 | §3 の採否基準を全部満たすこと |
| 再確認期限の延長 | 会場・主催者の公式ページで開催を確かめたときだけ |
| `hook` / `relation` の下書き | §4 の型の中で書く。掲載前に編集部が読む前提 |
| テストの契約更新 | §2-B の条件を満たすときだけ |
| 実装・リファクタ・回帰修正 | 課題1つ・ブランチ1つ。スコープを広げない |
| 検知・監視の道具を足す | 検査を強める方向のみ |
| ブランチへの push | 上記の成果物として |

## 2. 越えてはいけない線

### A. 承認なしには絶対にしない（`CLAUDE.md` から）

1. `main` への merge、Production への deploy
2. PR を自律的に作る
3. force-push
4. 権利の不明な画像・映像・音源を使う
5. 外部へのデータ送信を増やす。利用者が書いた文・写真・私的な情報を外部へ出す
6. GA4 のイベント定義を変える
7. 端末内保存のキー・形式・削除の挙動を変える
8. 診断、感情スコア、心理推定、連続記録、ランキング、ゲーミフィケーションを入れる
9. Product meaning / Brand / Art Direction / Visual Canonical を変える
10. テストを削除・skip して緑にする
11. 裏付けのない関係・経路・橋渡しを出す

### B. 今日の経験から、自分で足す線

上の11に加えて、**次の6つを守る。** どれも今日の作業で、
守らなければ間違えていた（あるいは実際に間違えた）ものである。

**(12) 「できない」と結論する前に、経路を2つ試す。**

今日、『女優魂2026』を「上映日程が PDF にしかなく読めない」として見送った。
実際は特集ページの HTML に、作品ごとの上映日と時刻がそのまま載っていた。
PDF を開こうとして失敗した時点で結論を出し、同じページの本文を読まなかった。
**見送りは安全側の判断に見えるので、間違っていても気づきにくい。**
できないと書く前に、別の経路を1つは試す。試した経路を記録に残す。

**(13) 検査を弱める変更は、1回の作業で3件まで。超えたら止めて報告する。**

今日 `qa/ga4_v3_client_selftest.js` の許可リストに5回追加した。
1件ずつは正当だった（生成物や新しい道具を許可しただけ）。
しかし**これは検査を弱める操作であり、積み重なると検査が意味を失う。**
作業のたびに緩めるのが習慣になると、誰も気づかないまま骨抜きになる。
`repeatable`、`allowed`、期待値の緩和、閾値の引き下げはすべてこれに数える。
**実態に合わせて数字を更新することは含めない**（件数を実数に直すなど）。

**(14) 自分が書いた下書きを、自分で承認しない。**

`hook` と `relation` は下書きまでが私の仕事である。
テストが緑でも、自分の文章を「確認済み」として扱わない。
引き継ぎ書の「編集部の判断待ち」に残したまま次へ進む。

**(15) 確認できなかったことを、確認したと書かない。**

`shimokita-moon` は会期が残っているのに期限を延ばさなかった。
`moonartnightfes.com` に接続できず、開催を確かめられなかったからである。
`checkedAt` には実際に確かめた日だけを書く。
届かなかったドメインは、届かなかったと記録に残す。

**(16) 予約・公開済みのものが名指ししている事実を、あとから動かさない。**

**公開物が数字や事実を名指ししているなら、それを動かす前に公開物を直す。**
順序を逆にしない。直せないなら、動かさない。

経緯：10月のX原稿は当初、10/31 の稿が作品数を「77件」と言っていた。
作品を1件足せば、その投稿は事実と違うことを言うことになる。
**ファウンダーは予約時に数字そのものを本文から外した**（2026-09-11）。
数字を持たない書き方にすれば、後ろの作業を縛らずに済む。
**これが本筋である。** 公開物を先に縛らない書き方を選べるなら、そちらを採る。

同じ日、10/22 の稿でも同じことが起きた。「明日から3日間開催！」と書いていたが、
会期 10/23〜11/1 は10日間で、3日間は誤りだった。ファウンダーは日数を直すのではなく
**「明日から開催！」と、日数を言わない形にして解消した。**
数えられる事実は本文の「日時：10月23日（金）〜11月1日（日）」が持っている。
**動かない事実は書き、動く数字は持たない。** これが型である。

その結果、いま作品追加を止める制約は無い（2026-09-11 時点）。
新しく数字を出す公開物ができたら、この線がまた効く。

**(17) 自動で動くときほど、止まる条件を先に決める。**

週次の自走（§5）では、判断に迷ったら push せずに報告する。
「とりあえず出して人に直してもらう」はしない。
迷いは、基準が足りていない印である。基準を足すのはファウンダーの仕事。

## 3. 催しの採否基準

`EVENT-SOURCES.md` の8項目と `SELECTION-20260910.md` の考え方を、
催しに当てはめて機械的に判定できる形にした。**全部満たしたときだけ採る。**

### 満たすこと

1. **会場が4街（高円寺・下北沢・吉祥寺・神保町）の中に実在する。**
2. **主催者または会場の公式ページで、8項目すべてを確認した。**
   題名 / 街 / 会場 / 開催日（全日付）/ 時刻・回 / 種類 / 公式URL / 料金・年齢条件
3. **出典は主催者・会場の公式ページ。** enjoytokyo・walkerplus・gotokyo などの
   一覧サイトは出発点であって出典ではない。そこで見つけても、公式まで辿ってから書く。
4. **街との関係を、事実として言える。** 言えないなら採らない。
   関係が「上映館・会場である」だけなら、**そう書く。**
   撮影地・舞台だと読めてしまう書き方をしない。
   既存の `jinbocho-pokemon` の「街との接点は撮影地ではなく、この映画館の特集上映です」が型。
5. **既に載せた催しと、同じ出来事・同じ発信元でない。**
6. **画像は既存の権利確認済みのものだけを使う。**
   会場写真があれば `tools/event-media-source.js` の `byId` に結ぶ。
   なければ街の写真に落ちる。**新しい画像を探して足さない。**

### 採らない

- 8項目のどれかが確認できないもの。**件数のために基準未満を残さない。**
- 公式ページが読めない、または動的生成で日程が取れないもの
  （現状シネマリスがこれにあたる）。読めない理由を記録して見送る。
- 会期が既に終わっているもの、再確認期限を自分で延ばせないもの

### 採ったあとに必ず確かめる

```sh
node qa/verify-product.js
node qa/event_supply_check.js
node tools/build-weekly-outings.js --check   # 生成物4本すべて
```

在庫の下限は二つある。**全体で週5件**（`event_supply_check` が今週・来週で落とす）と、
**街ごとに週3件**（`weekly_outings_check`）。先の週ほど薄くなるのは自然なので、
落とすのは近い週だけでよい。ただし薄い週が「来週」になる前に足す。

## 4. 文言の型

`hook` と `relation` は編集部のものである。私が書くのは下書きまで。
型を外れそうなら書かずに止める。

### hook（一文）

- **その催しで何に出会えるかを、一文で言う。** 誇張しない。感想を書かない。
- 「必見」「話題の」「人気の」は使わない（ランキングを持ち込まないため）。
- 読者を決めつけない。「〜なあなたへ」と書かない。
- 例：「昼から始まるライブで、生演奏に出会う。」「台所から、もう一つの土地の暮らしを知る。」

### relation（なぜこの街か）

- **事実だけで書く。** 誰が、何を、どこで。出典で言えないことを足さない。
- **関係の種類を正直に書く。** 会場であるだけなら「この映画館の特集です」と書く。
  撮影地・舞台・ゆかりの地に見せない。
- 推測で街や会場に紐付けない（`CLAUDE.md`「NO EVIDENCE = NO BRIDGE」）。
- 例：「中川敬（ソウル・フラワー・ユニオン）とリクオによる公演を、
  高円寺のライブハウスJIROKICHIで開催します。」

### practical（料金・条件）

- 確認できた金額と条件だけを書く。**確認できないものは「公式で確認してください」と書く。**
  推測した金額を書かない。
- 年齢制限・入場条件は、公式の書き方に沿う。緩めて書かない。

### companionNote

- 過ごし方の提案であって、読者の属性の決めつけではない。
- 「ひとりでも」「友人と」程度にとどめる。家族向けと書くのは、公式が対象年齢を
  そう示しているときだけ。

```sh

node qa/event_supply_check.js                                # 6週の見通し
```

### 見つけたらどうするか

| 出たもの | すること |
|---|---|
| 期限の固まり（21日以内・3件以上） | 公式ページで開催を確認し、確かめられた分だけ期限を延ばす |
| 薄い週（全体5件・街3件を割る） | §3 の基準で補充する |

| テストの回帰 | 直す。直せない理由があれば止めて報告 |
| 判断に迷うもの | **push せずに報告する**（§2-B 17） |

### 出しかた

- ブランチへ push する。**`main` には触れない。PR も作らない。**
- 変更が無ければ何もしない。**報告のために無理に何かを変えない。**
- 報告は `CLAUDE.md` の6項目（変更ファイル／変更内容／テスト結果／
  端末内保存・棚・Object契約・GA4・外部通信への影響／残る懸念3つまで／Preview可否）。

### 止まる条件

次のどれかに当たったら、その場で止めてファウンダーに報告する。

- 権利が不明な素材に触れそうなとき
- §2-A の11項目のどれかに触れそうなとき
- 検査を弱める変更が3件を超えそうなとき（§2-B 13）
- 公開済み・予約済みのものが名指しする事実を動かすことになるとき（§2-B 16）
  ※ 2026-09-11 時点で、作品追加を止める制約は無い（10/31 の稿から数字が外れたため）
  ※ 公開物を書くときは、動く数字を本文に持たせない。持たせると後ろの作業が縛られる
- 基準（§3・§4）で判断がつかないとき
