# 感情書店：存在理由・運営・判断基準（R8）

更新：2026-09-08。ユーザーの最新指摘を受けた方針決定。以下の数値は運営の仮説・判断用の目標であり、実績・需要証明ではありません。
この文書を従来の「掲載数を増やす」「月22〜31時間」の計画より優先します。

## 何のサイトか

**心が動く作品に出会い、その気持ちを街での体験へつなげ、持ち帰れる文化案内。**

「書店」は、気になるものを手に取り、次の好きを見つける場所という意味。本・音楽・映像・映画を扱う。見ただけで帰る日も成功。現地訪問や購入を必須にしない。
「感情」は、感動するはずと誘導するコピーや感情診断ではなく、作品を見た本人が「自分にはこれが残った」と感じる余白。
目指す変化は、訪問前には知らなかった作品や街への関心が一つ生まれ、自分の言葉や次の行動になること。

## 他のメディアとの違いは、検証すべき価値仮説

場所の網羅性、ニュース量、SNSの投稿量では競わない。既存サービスより優れているとまだ証明できていない。
このサイトで担うのは「まず作品を楽しむ → 根拠のある街との関係を知る → 今の催しや公式の深掘りへ → 自分のひとことを持ち帰る」という編集。

- 井の頭公園：有名な公園だからは採用理由にならない。映画『PARKS』の制作背景・場面との関係や、そこで行われる実際の文化企画を入口にする。
- 高円寺と吉祥寺：同じシェイクスピア原作の異なる上演を辿る。地理的に近いだけではつながりと呼ばない。
- 企業広告：人・身体表現・物語として見る価値を説明できる場合に選ぶ。業種が不動産だから「街」と関連付けない。
- 映画特集：舞台・撮影地・上映館を混同しない。映画館での上映だけなら、その接点をそのまま示す。

## 今回の実装と、まだ実装しないもの

| 採否 | 内容 | 理由 |
| --- | --- | --- |
| 実装 | HOMEの役割を一文と作品入口で提示、感情書店とはを別ページへ | 理念を長々とHOMEに積まない |
| 実装 | 詳細ページの任意スタンプ・メモを共有・コピー・カレンダーへ | 個人の感想をサーバーに集めず、利用者が持ち帰れる |
| 実装 | 実在24催し、週・街・同行者で選択、一覧→詳細 | 汎用スポット紹介から、日付と理由のある文化体験へ |
| 実装 | 共通のトップ・上部へ戻る、選択条件を保つ戻り先 | 迷っても入口へ戻れる |
| 次段階 | 作品固有の画像・所要時間、映像の公開状態の継続点検 | 文章や汎用ジャンル写真への依存を減らす |
| 次段階 | 公式情報からの候補収集・差分検知 | 新規掲載の手作業を減らす。未検証情報の自動公開とは分ける |
| 保留 | 気分の多段診断・個人プロファイル | まず一本楽しむまでの操作を増やさない。必要なら「静かに観たい」等の自己選択だけを小さく比較 |
| 保留 | Instagramの保存一覧・ピン留め同期 | 公式に取得可能な対象、権限、利用者の需要を未確認。連携できると約束しない |
| 保留 | noteへの自動投稿、独自SNS、公開感想欄 | コピーとリンクで持ち帰る体験を先に検証。アカウント管理とモデレーション負担を増やさない |
| 限定採用 | 街の文化トピック | 作品・場所・文化活動の変化に限る。一般経済の見出し一覧は作らない |

スタンプは「心に残った」「元気をもらった」「誰かに伝えたい」「行ってみたい」。複数選択・取り消しができ、文章なしでも共有・コピーできる。公開リアクション数や人気ランキングは作らず、選択・文章は自動保存・送信しない。

持ち帰り先：端末の共有メニュー（対応するメモ・日記・管理アプリ）、クリップボード、Googleカレンダーの予定作成画面、Apple等の対応カレンダー向け.ics。独自アカウント・保存先アプリの認証情報を要求しない。
カレンダーは利用者が選んだ日の「終日のメモ」。公演時刻や予約が確定した予定と誤認させない。予約・空席は公式案内、保存先と公開範囲は利用者側アプリで確認する。
共有API非対応環境ではコピーを案内する。アプリ一覧は端末依存で、全日記アプリへの直接連携を保証しない。Googleへの遷移・端末の共有・ファイル出力はいずれも利用者の操作時だけ。保存完了や投稿完了をサイト側で測定・断定しない。

## 利用場面（属性による決めつけではなく仮説）

| 利用する人・場面 | 最初の体験 | 次の行動 | 成功の見方 |
| --- | --- | --- | --- |
| 中学生、家で友人と共有したリンクから | 無料の短い公式映像や好きな作品の背景 | 気になった理由をメモ。行くなら年齢条件が合う昼の企画を家族と相談 | 難しい説明なしに一本楽しめる |
| 高校生（性別を問わず）、放課後や休日の前 | 知っている映画・音楽から別の表現を知る | 友人に作品リンクを送り、参加条件が合う催しを考える | 「知らなかった、見たい」が一つ生まれる |
| 大学生、講義の合間や週末前 | ライブ映像、短編、舞台と本の接点 | 友人や恋人との予定を選ぶ | 予算・日時を公式で確認できる |
| 社会人、帰り道の5分 | 一曲・一本を楽しむ | ひとことを持ち帰る、週末に続きへ | 現地へ行かなくても再訪したい |
| 子どもと出かける大人 | 親子上映、絵本作家の公開制作 | 年齢条件・予約・時間を確認 | 一般的な公園紹介では得られない具体的な体験を選べる |
| 海外からの訪問者 | 英語の街の文化説明と公式案内 | この街ならではの作品・歴史を辿る | 「東京のどこでも同じ」にならない |

初期の検証は大学生・社会人の短時間利用と週末前の利用を中心にする。全世代同時に最適化しようとしてHOMEを複雑にしない。年齢・性別・気分を取得するターゲティングは追加しない。

## 飽和しない編集

- 常設：各街の音楽・映像・本・映画は各5〜10件の選定。追加だけでなく入替。作り手・シリーズ・会社の偏りも点検。
- 旬：開催中・近日開催のイベント。終了したら現役一覧から外し、過去の記録と区別。
- 関係：作品・人・場所・出来事を、出典と関係の種類を持つデータにする。作品の名寄せをして一つの作品を街ごとに重複管理しない方向へ。
- HOME：作品入口、街、厳選した文脈と催し入口。ニュース・ジャンル・街が増えるたびにHOMEの段を増やさない。
- 追加できる良いものがない週は、更新量を減らす。最低件数のために無関係・非公開・未確認を混ぜない。

## 運営：現在と目標

### 現在動く実装

- 日本時間の月曜に開催週を切り替える。開きっぱなしでも日付を見直す。
- 実際の開催日と休館日で絞り、終了・中止・確認期限切れを一覧から除く。
- 元データは tools/weekly-outings-source.js。開催日、会場、公式URL、確認日、確認期限、掲載理由を持つ。
- tools/review-culture-events.js が今週・翌週の4街の件数、確認期限、任意でURL到達を点検する。HTTP 200を開催継続の証拠として扱わない。
- GitHub Actionsに月曜00:10・金曜09:10 JSTの点検を用意。結果は実行画面と保存レポートへ。デフォルトブランチへの反映とActions有効化後に動く。現時点で定期稼働したとは扱わない。

### 次に自動化する作業

公式・施設の許可されたRSS/API/公開告知から候補収集 → 重複・日時・変更の差分 → 街と文化の関係の根拠候補 → 掲載原稿の下書き → 自動検証 → 差分確認。
収集は登録した出典に限定する。日付・場所・本文の解釈に曖昧さがあれば候補止まり。AIが「行って楽しかった」と架空の体験談を作らない。

自動化の順序は「運営者の全件巡回を、要対応の差分だけを見る仕事へ変える」。オーナーがコードを毎週貼り付ける運用を完成形にしない。
当面の選定・内容再確認はAI支援の編集工程が残る。完全無人で新しい良質な特集を出し続けられる状態には未到達。
一度の公開後に無期限で正しいとは約束しない。収集不能時は期限切れを隠し、常設作品を楽しめる縮退状態にする。

### 負担と継続性の目標

初月は調査・修正・公開判断の実作業時間を記録。定常運営はオーナー確認を週60分以内にする仮目標。超えたら都市追加や記事本数より、情報源・入力形式・更新頻度を減らして整える。
費用上限はオーナーが指定するまで追加課金の契約をしない。ホスティング、外部API、AI、手動対応の実費と時間を月次で同じ台帳に記録する。

## 街の記事・ニュースの採用条件

掲載するのは、その街で作品に触れる体験が変わる情報。映画館の特集、本屋の新企画、劇場の活動、作り手の話、街の記憶の更新など。
経済ニュースは、文化施設の閉館・移転や文化を支える仕事など、具体的な体験への影響を出典で説明できる場合に限る。
小ネタも、出典があり、一つの作品・場所を違って見られるものを選ぶ。

当初は各街ページ内の「街の文化トピック」に最大3件という設計。HOMEへ新しいニュース枠を追加しない。見出し＋短い紹介＋日付＋元記事のリンクを基本とし、本文の転載を自動生成しない。
候補収集と失効は自動化するが、根拠のない要約や時期不明の情報は公開しない。現段階ではニュース欄そのものは未実装。

## どう知ってもらうか

1. 検索：作品名と街の関係、具体的な催し、作り手の固有情報がある詳細ページを整える。ページ数だけ増やすSEOをしない。
2. 共有：一本・一冊・一つの催しの安定URLと、利用者が書いたひとこと。相手に伝わる単位を小さくする。
3. 編集発信：Instagramは権利を確認したビジュアルと短い入口、noteは作品と街の関係を深める文章という役割案。利用者の保存を取り込むこととは別。自動投稿や外部連絡はまだ行わない。
4. 地域との接点：掲載館・書店・作り手が自分の公式案内と一緒に紹介したくなる正確さを作る。相互リンクや協業の打診は、内容を用意してから実施判断する。
5. 流入数だけでなく、どの入口が次の作品との出会いになったかを検証する。

連携調査：Instagramの公式プラットフォーム文書はビジネス/クリエイター向けの管理機能を中心に案内。一般利用者の保存一覧同期を実装可能と確認したわけではない。

## ゴールと、止める判断

第一の成果は「一つの出会いを持ち帰れた人が、また自分の意思で使うこと」。閲覧時間の長さ、プレイヤーの読込、外部クリックだけで感動・実再生・現地訪問を推定しない。
既存の匿名計測と、任意の利用確認を分ける。今回、自由記述・感情・年代の計測を追加しない。

| 段階 | 仮の判定基準 | 未達時の判断 |
| --- | --- | --- |
| 初見理解 | 10人中8人が、説明を受けずサイトの役割と最初の操作を言える | 機能を増やさず、コピーと入口を見直す |
| 最初の体験 | 既存計画の12人・14日試用で、8人以上が3分以内に気になる作品を開く | 絞り込み・作品の選定・読み込みを改善 |
| 継続の兆し | 同試用で4人以上が催促なしに再利用。数字は初期判定の仮置き | 需要が証明されたとせず、利用場面を狭める |
| 運営成立 | 4週間、重大な掲載誤りなし。オーナー確認が週60分以内という目標 | 情報源・街・更新頻度を縮小し、仕組みを改善 |
| 90日判断 | 少なくとも二度の改善後にも理解・再利用・運営負担が改善しない | 機能拡張を止め、常設の小さな選書サイトに縮小する案をオーナーへ提示 |

サイトを閉じる、収益化する、課金契約する判断を数字だけで勝手に実行しない。目標・負担を見てオーナーが最終判断する。

## 10年に向けて残すもの

年ごとの流行に依存する無限記事ではなく、出典付きの作品・人・場所の関係データ、変更履歴、安定したURL、持ち出せる利用者の言葉。
イベントは期限を持つ。運営者やAIモデル、外部SNSが変わっても、データを引き継げるようコードとデータを分け、JSON/CSV/Markdownで書き出せる形を維持する。
四半期ごとに出典の生存率・偏り・運営時間・費用を確認。毎年、バックアップからの復元と古いリンクの移行を確認する。都市を追加する条件は、出典供給と編集負担が既存4街で安定していること。
10年運営できると今から証明はできない。特定SNSへの依存を減らし、少なく保てる構造を作ることを今の設計基準にする。

## 共有・持ち帰りの実装参照

- 端末共有：MDN Navigator.share()。HTTPSと利用者操作が必要。共有先・完了の意味は環境に依存する。https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share
- 予定ファイル：IETF RFC 5545。終日はDATE型、終了日は翌日。UTF-8を壊さず75オクテットで折り返し、自由記述をエスケープする。https://datatracker.ietf.org/doc/html/rfc5545
- Googleカレンダーの予定作成URL：Google Developersコミュニティで案内される形式。OAuthによる予定APIへの自動書込みではない。実端末での保存完了は未確認。https://discuss.google.dev/t/enabling-app-users-to-add-google-calendar-events-from-your-app/62987

## 関連する人の声（Bluesky）

詳細ページの補助として、確認済みの公開投稿を1ページ1件まで。最初は『ムーンアートナイト下北沢2026』を紹介するConnecting The Dots | Art & Designの投稿を掲載。第三者による紹介として表示し、主催者発信とは呼ばない。作品・イベントに直接関係する主催者・会場・作り手の投稿を優先し、適した投稿がないページに空の枠を作らない。
無料の公式埋め込み方式を利用し、Xの有料API・第三者ウィジェットの契約・SNS認証は追加しない。初回表示では接続せず、利用者が表示ボタンを押すとBlueskyに接続。1投稿と元の会話への出口で止め、返信を丸ごと再配信したりキーワード検索の生の流れを載せたりしない。
投稿者・投稿日を表示し、掲載理由・公開確認日・確認期限を元データに記録。期限切れはブラウザーで隠す。削除や埋め込み拒否は本人・配信元の状態を尊重し、本文をコピーして復元しない。利用者のメモやスタンプを埋め込みへ渡さない。
